# Source Code Editing

Use the `run-realm-code` tool for every source-file creation or edit. Do not emit file edits as prose. The tool executes JavaScript in the isolated realm runner. Each `realm.fs` call goes to the host, which reads files in the given realm and saves each write before the call returns.

The script runs in a small QuickJS sandbox, not in Node.js or a browser. The script is the body of an async function, so you can use `await` and `return` at the top level. The only globals that the sandbox adds are `realm` and `room`. Never declare a variable named `realm` or `room`: it hides the API, and the next `realm.fs…` call fails with `cannot read property … of undefined`; name a URL `catalogUrl` or `workspaceUrl` instead; the standard JavaScript built-ins (`JSON`, `Math`, `Date`, `RegExp`, `Promise`, and so on) also work. There is no `console`, `print`, `nodeRepl`, `process`, `require`, `import`, `fetch`, `setTimeout`, DOM or Node API. A call to one of these stops the script with a `ReferenceError`. The tool result shows only the value that the script returns, as JSON, and nothing else. To see a value, `return` it, for example `return { files: await realm.fs.list() };`. A script that does not return a value gives a result with no value.

Before editing, read the current contents of every target file with `await realm.fs.readText(path)` in the script. To see what a folder holds, call `await realm.fs.list(path)`; with no path it lists the realm root. It returns one `{ name, path, kind }` entry for each file and folder directly in that folder, where `kind` is `'file'` or `'directory'` and `path` is relative to the realm root (a folder's `path` ends with `/`). To read a card instance as data, call `await realm.cards.get(path)`, where `path` is the instance with or without `.json` (`Person/sample`). It returns `{ id, path, type, attributes, relationships }`: `type` is `{ module, name }` of the card's definition, `attributes` holds the field values, computed fields included, and `relationships` maps each link's field path to the linked card's URL (`field.0`, `field.1`, … for a `linksToMany` field). Every URL is absolute. It reads the indexed card, so a card you just wrote can take a moment to index; then it fails with `Card is not indexed yet`, and you read it again. It also fails for a card that is not found or has an error, with that error's message. To read or list without writing, return the result from the script, for example `return await realm.fs.readText('person.gts');`, and read it in the tool result. Pass the workspace realm URL and room ID supplied by the host. Use `await realm.fs.replace(path, exactCurrentText, replacement)` for an existing file. Use `await realm.fs.writeText(path, content)` for a new file; it refuses a file that already exists. To duplicate a file, call `await realm.fs.copy(fromPath, toPath)`. Both paths are in the run's realm. It refuses a `toPath` that already exists and a binary file, and it needs write access. It copies the content as it is: relative imports, `adoptsFrom` modules and card links are not changed, so they stay correct only when the copy is at the same folder depth as the original. To change the copy, call `realm.fs.replace` on `toPath` in the same script. To copy a file to another realm, use two runs: read it with `realm.fs.readText` in a run in the source realm, then write it with `realm.fs.writeText` in a run in the target realm, with each relative module and link path changed to an absolute URL in the source realm. `path` is relative to the realm root, such as `person.gts`; a full file URL inside the realm also works. File content often contains backticks and `${`, for example a BXL `fx` expression or a template string in a computed field. If you put such content inside a JavaScript template literal, escape each backslash in it as `\\` first, then each backtick as `` \` `` and each `${` as `\${`. Without this, the script does not parse, or it saves different text without an error: `/\d+/` becomes `/d+/`, and `${name}` is replaced with a value. Escape the `exactCurrentText` argument of `realm.fs.replace` the same way, or it does not match the file. Use `await realm.fs.writeBytes(path, base64)` for a new binary file, such as an image: `base64` is the file's bytes as a base64 string, or a `data:` URL with base64 content. It refuses a file that already exists, a file larger than 2,000,000 bytes, and more than 5,000,000 bytes in one call. `readText` and `replace` refuse a binary file. Use `await realm.fs.delete(path)` to delete a file: one that this run created, such as a file the script wrote by mistake, or one that was there before the run, such as a file an earlier run wrote by mistake. It returns `{ path, deleted: true }`, the tool result lists the file with the status `deleted`, and the file does not exist. A delete cannot be undone, so delete only a file that you are sure is wrong, and tell the user which file you delete and why. First read a text file with `realm.fs.readText` in the same script: if someone changes the file after that read, the delete is refused with `File changed while the script ran` and the file stays. It refuses a folder and a file that does not exist. Write the call exactly as `realm.fs.delete(...)` in the script. A run whose code contains that text always waits for the user to approve it, also in act mode. A run that gets to the delete in a different way is refused. After the delete, the same script can write the path again with `writeText` or `writeBytes`; the tool result then lists the file as saved. A path counts once toward the 20-file limit, however many calls use it, so a delete and a new write to the same path count as one file. To fix a file instead of deleting it, change its content with `realm.fs.replace`. To move a file, copy it to the new path with `realm.fs.copy` and delete the old one with `realm.fs.delete`. Use `await realm.fs.exists(path)` to check whether a file exists. Await every call. Write all files of a build in one call, within the limits of one call: at most 20 files (each file path given to `readText`, `exists`, `replace`, `writeText`, `copy`, `writeBytes`, `delete`, `images.generate` or `download` counts; `list` and `cards.get` do not; a path counts once, however many calls use it, and each image counts once, as the path it is saved at), a script of at most 100,000 characters, and 55 seconds. Split a larger build across calls. To show the user a card when the run ends, return `{ show: path }` with the instance path, for example `return { show: 'Pet/mango' };`, from the call that writes it; there is no separate call to show it. The host opens it after it checks that the card is an instance in this realm; if it cannot, the result's `showError` says why and the files stay saved. A `.gts` or `.ts` write with lint errors that autofix cannot repair is refused, and the script stops there. Each write is saved when its call returns, so if the script fails partway, the files written before the failure stay saved; the error names them. The error names in separate lists the files that the run created and then deleted before the failure, and the files from before the run that it deleted; those files do not exist. To fix a file the failed run saved, change it with `realm.fs.replace` in the next run, or delete it with `realm.fs.delete`.

To find cards in the realm, call `await realm.cards.search(query)`. `query` is a card query: a `filter` built from `on`/`type`, `eq`, `contains`, `range`, `in`, `any`, `every`, `not` and full-text `matches`, an optional `sort`, and an optional `page` (`{ size, number }`, where `number` starts at 0). The query syntax is in `boxel-environment/references/searching-and-querying.md`. It answers `{ cards, total, truncated }`. Each card is `{ id, path, type, attributes, relationships }`: `id` is the card's URL; `path` is its `.json` file relative to the realm root, which `realm.cards.update` and `realm.fs.readText` take; `type` is `{ module, name }` with a full module URL, so you can pass it back as a query's `type` or `on`; `relationships` maps each link field's path to the URL of the card it links to; a `linksToMany` field's links are keyed `field.0`, `field.1`, and so on. The data comes from the realm's index, not from the file: `attributes` include computed fields, and a card saved a moment ago can still show its old values. To change a card, pass only the fields you change to `realm.cards.update`, never all of `attributes` back. A card that failed to index is not in the results. A page holds `page.size` cards, 50 when the query names none, and never more than 100; `truncated` is `true` while more cards match past this page, so ask for the next `page.number` until it is `false`. A page too large to return fails with the `page.size` that fits. A search searches only the realm the script runs in; to search another realm, run another script in that realm. A search does not count toward the 20-file limit.

To change field values of a card instance, call `await realm.cards.update(path, attributes)`. `path` is the instance with or without `.json` (`Recipe/pasta`), or `card.path` from a search. `attributes` holds only the fields you change, as plain JSON: a nested object merges into the field's current value, and an array or any other value replaces it. It changes attributes only, not links; to change a link, edit the `.json` with `realm.fs.replace`. Use it instead of `realm.fs.replace` for every change to an instance's field values, because it needs no JSON escaping and no exact search text. It returns `{ path, fields, saves }`. Nothing is saved while the script runs: when the script finishes, the host saves every update in one request, all or none. If the script fails, or a card changed while the script ran, no update is saved. In the same run, `realm.fs` cannot read or change a card that has an update waiting, and `realm.cards.get` returns the card without the update. A run updates at most 200 cards, and they do not count toward the 20-file limit; more calls on one card count once. To change many cards, search, update and report in one script:

```js
const updated = [];
let more = true;
for (let number = 0; more && updated.length < 200; number++) {
  const { cards, truncated } = await realm.cards.search({
    filter: { on: { module: realm.current.url + 'recipe', name: 'Recipe' }, eq: { cuisine: 'unknown' } },
    page: { size: 100, number },
  });
  const room = 200 - updated.length;
  for (const card of cards.slice(0, room)) {
    await realm.cards.update(card.path, { cuisine: 'Italian' });
    updated.push(card.path);
  }
  more = truncated || cards.length > room;
}
return { updated, more };
```

Page inside this one script, as above, until `truncated` is `false` or the run reaches 200 updates. The index does not change while the script runs, because nothing is saved until it ends, so each page continues where the last one stopped. Run the script again only when it returns `more: true`. A later run starts again at `page.number: 0` when the filter selects on a field the script changes, as `cuisine` above: the cards the first run saved no longer match, so the next `page.number` would skip cards that still need the change. When the filter does not select on a changed field, the later run starts at the next `page.number` instead (2 after a run of 200 cards). A card the realm has not reindexed yet can match again; updating it again changes nothing.

Return only what you need from a search, such as the paths or a few attributes; the whole result goes into the tool result.

To look at what the script made, call `await realm.capture(target, options)` after the write. `target` is a path in this realm (`Pet/mango` for a card, `brand/guide.html` for a file), or a card id or file URL in any workspace the user can read, such as a catalog card or a file in another workspace; a target in no readable workspace is refused. `options` is optional: `format` (`isolated`, the default, or `embedded`; `fitted` cannot be captured), `viewportWidth`/`viewportHeight` (default 1280×800, a laptop screen), `fullPage`, and `target`, a CSS selector read from the card's template (`'.pricing'`): the capture is of the first element it matches, scrolled into view and cropped to it. `target` works on cards only (a file renders in its own frame) and cannot be combined with `fullPage`. A capture more than twice as tall as it is wide and taller than 4096px is cut to its top, and the result says so; any other capture too large to show is scaled down whole. To see a card, view an instance (`Person/sample` or `Person/sample.json`); viewing a `.gts` path shows the module's source file, not the card it defines. It attaches the image to the tool result, so you see it alongside the result; the script gets back only `{ path, kind, format, viewportWidth, viewportHeight, target, width, height, attached }` (`target` only when given), never the image. A capture shows nothing to the user; to put a card on screen, return `{ show: path }` or ask for a `realm.ui` action (below). A run can capture at most 3 times, and each capture spends the run's 55 seconds; a fourth capture, or one with too little time left in the run, is refused: capture the rest in another run. A card you just wrote can take a moment to index; if its capture fails, capture it again in your next run.

Capture what the conversation is about, not only the top of a laptop-width page:
- **At the width the work is about.** When the user is working on how something looks on a phone, capture at a phone viewport (about 390×844); on a tablet, about 820×1180. A layout that changes with width looks right at 1280 and can be broken at 390, so check each width the change affects.
- **The part being discussed.** A section below the top of the page does not show in a default capture: give its selector as `target`, or capture with `fullPage` when you need the whole page.

Capture freely, without asking first, also in a run that writes nothing. You cannot judge visual work from source alone:
- **To see context that carries visual meaning** — a brand guide, a theme, a layout, a card the user points at, an image or an HTML page in the workspace. Look before you describe it, match it, or build on it.
- **To check your own output** — after you create a card or change how one looks (a template, styles, an image, an HTML file, content that drives the layout), look at it and compare it with what was asked. A data edit that changes nothing visible needs no capture. Fix what you see before you report back. Capture in the same script that made the change, right after the write.

You see an image in the turn it arrives. In later turns the conversation keeps only its name and size, so to look again, capture it again. At most 8 images reach you per turn, the newest first; view only what you need for the step you are on.

What you can and cannot see:
- **Anything in a workspace:** capture it with `realm.capture`, as often as you need.
- **An image or PDF the user attached to the chat:** you see it in the turn they send it. To look at it again later, ask them to attach it again, or to upload it into the workspace so you can capture it whenever you need.
- **Any other file the user attached from their computer** (an HTML page, a document): you receive only its source, never how it renders. Say so plainly — tell the user you cannot see it rendered — and ask them either to attach a screenshot or to upload the file into the workspace, so you can capture it yourself. Never describe how it looks from its source as if you had seen it.
- **An image you were told was not sent to you:** the note gives the reason.
  - *The active model does not accept images:* stop viewing. Tell the user once that the current model cannot see images, and offer to switch to one that can (`room.setModel`).
  - *Newer images filled the turn, or it was too large:* view it again on its own, or a smaller viewport of it, in your next step.
  - In every case, do not guess at what it shows.

To find what exists across realms and the catalog — Specs, cards, files, listings — call `await realm.entries.search(query, { realms, scope, limit })`. `query` is a card query, without `page`: a `filter` built from `on`/`type`, `eq`, `contains`, `range`, `in`, `any`, `every`, `not` and full-text `matches`, and an optional `sort`; the syntax is in `boxel-environment/references/searching-and-querying.md`. A query with `page` is refused. `realms` is an array of realm URLs and defaults to every realm the user can read, the catalog included; `scope` is `'cards'`, `'files'` or `'all'` (the default); `limit` is how many entries to return, 20 when missing and never more than 50. It answers `{ entries, total, truncated, incomplete }`. Each entry is `{ url, kind, ref, specType, cardTitle, cardDescription, name, readMe }`, where a Spec's `ref` is the export it describes and `readMe` is its full readMe. `truncated` is `true` when more entries match than the answer holds: narrow the query rather than ask for more. `incomplete` is `true` when a realm did not answer. The search does not write and does not count toward the 20-file limit. Run all the searches a task needs in one script and return only what you will use; see `boxel-ui-component-discovery` for a loop.

To make an image, call `await realm.images.generate({ prompt, path, sourceImageUrl, llmModel })`. `prompt` and `path` are required; `sourceImageUrl` (an image to start from: a `data:` URL, or a file in this run's workspace, as a path or a full URL; any other URL, such as a public `http(s)` image, is refused) and `llmModel` (an image model id) are optional. The host asks the model for the image and saves it as a new file at `path`; the file extension follows the image type the model returns, so `Pet/mango.png` can be saved as `Pet/mango.jpg`. Before it asks the model, it refuses a path where a file already exists, also with another image extension (`Pet/mango.jpg` blocks `Pet/mango.png`), so no credit is spent on an image that cannot be saved. It returns `{ path, contentType, size, saved: true }`, never the image: link the returned `path` in the card JSON in the same script. `path` is relative to the realm root, so a link from an instance in a folder needs `../` in front of it (`sample-images.md` in `boxel-file-def` has the steps). Each image spends the user's credit, so a run whose code contains `realm.images.generate` always waits for the user to approve it, also in act mode; write the call exactly by that name, because a run that gets to it in a different way is refused. A run can generate at most 4 images, and a run that generates images gets 120 seconds for them on top of its 55 seconds, at most 60 seconds for each image. The realm calls of a run go one at a time, also in `Promise.all`, so the images are made one after another within those 120 seconds; when the time is used, the next call is refused before it asks the model.

To save a file from the web into the realm, call `await realm.fs.download(sourceUrl, path)`. `sourceUrl` is an absolute `http` or `https` URL. `path` must have a file extension, because the realm infers the file type from it. The host fetches the file from the browser and saves it; the bytes never enter the script. Because the fetch runs in the browser, the source must allow CORS. It refuses a file that already exists, an empty response and a failed fetch, a file larger than 10,000,000 bytes, and more than 25,000,000 bytes in one run. Each download may take 20 seconds, and it counts toward the run's 55 seconds. It returns `{ path, size, saved: true }`; link the returned `path` in the card JSON in the same script. A run whose code contains `realm.fs.download` always waits for the user to approve it, also in act mode; write the call exactly by that name, because a run that gets to it in a different way is refused.

To refresh the index of this realm, call `realm.index`. `await realm.index.invalidate(paths)` indexes specific files again (a path, or an array of 1 to 100 paths); `await realm.index.reindex()` reindexes the realm; `await realm.index.fullReindex()` rebuilds the whole index from scratch; `await realm.index.cancelJob()` cancels the running indexing job. Each call needs write access, starts the work on the realm server and returns at once, with no wait for the indexing to finish. Use them when a card shows old data or an index error after an edit and the user asks to refresh it. Each call returns a small object when the realm server accepted the request (`{ invalidated: [paths] }`, `{ reindex: 'started' }`, `{ fullReindex: 'started' }` or `{ cancelled: true }`) and throws with the server's error when it did not. A cancel stops the indexing jobs the realm is running; jobs that wait in the queue stay there and run after it. A full reindex is slow and a cancel leaves the index without the work it stopped, so use them only when the user asks. A run whose code contains `realm.index.fullReindex` or `realm.index.cancelJob` always waits for the user to approve it, also in act mode; write these calls exactly by that name, because a run that gets to one in a different way is refused.

To create a workspace for the user, call `await realm.workspaces.create({ name, endpoint })`. Both options are optional: a random name is made when `name` is missing, and `endpoint`, the URL path segment, is made from the name when it is missing. It returns `{ url, name }`. Report the URL to the user. When the run ends, the host opens the new workspace. A run works in one realm only, so the script cannot write to the new workspace. To add files to it, run `run-realm-code` again with the new URL as `realm`. One run can create at most 5 workspaces.

To delete a workspace that the user owns, with all of its cards and files, call `await realm.workspaces.delete(url)`. It returns `{ url, deleted: true }`. A delete cannot be undone, so confirm with the user before you call it. Write the call exactly as `realm.workspaces.delete(...)` in the script. A run whose code contains that text always waits for the user to approve it, also in act mode. A run that gets to the delete in a different way is refused.

To change this chat room, call `room` in the script. `await room.enableSkills([id, ...])` turns skills on and `await room.disableSkills([id, ...])` turns them off; an id is a skill card id or a skill markdown file URL, at most 20 in one call. `await room.setModel(modelId)` switches the room to another model, such as `anthropic/claude-sonnet-4.5`; a model the room cannot use is refused with the list of models it can use. Change the room's skills only when the user asks for it; to use a skill yourself, read its `SKILL.md` with `readRealmFile` instead. These calls change only the room the tool was called from. Each call checks its input and records the change; the host makes the changes after the script finishes, and only when it finishes without an error. An error the script catches itself does not count: when a `try/catch` around the call returns normally, the changes are made. The tool result lists each change that was made. A skill you enable is available from your next step.

To show the user what the script made, end the script with `return { show: path }` (the instance path, such as `Pet/mango`), or ask for UI actions with `realm.ui` in the same script: `await realm.ui.switchSubmode('code')` (or `'interact'`), `await realm.ui.openFile(path)` to open a file in code mode, `await realm.ui.previewFormat(cardPath, format)` to open a card's definition with a preview of that card (`format` is `isolated`, `embedded`, `fitted`, `atom` or `edit`; `cardPath` is the instance path, such as `Pet/mango`), and `await realm.ui.openWorkspace()` to open the workspace the script runs in. Each `realm.ui` call checks its input when the script makes it, so a missing file fails at once. The host does the actions in order after the script finishes, and only when it finishes without an error; a run can ask for at most 10. The result's `uiActions` gives the status of each action; `shownCard`, or `showError`, says whether the show worked. This replaces a separate `switch-submode`, `preview-format` or `open-workspace` call after a build. Each tool result's `context.submode` and `context.codeMode.currentFile` tell you where the user is; do not ask for an action that changes nothing. To open a file or a workspace in another realm, run the script in that realm.

`run-realm-code` also runs in a workspace the user can only read, such as a catalog. There, reads, lists and captures work, and each write is refused with `You can only read this workspace`. Do not retry a refused write in the same workspace: tell the user, or write to a workspace the user owns.

Keep the script deterministic and narrowly scoped. Do not access browser globals, network services (other than through `realm.fs.download`), credentials, or files outside the given realm (other than through `realm.entries.search` and `realm.capture`). After the tool returns, inspect its result and address any correctness errors with another tool call.
