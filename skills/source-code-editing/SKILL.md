# Source Code Editing

Use the `run-realm-code` tool for every source-file creation or edit. Do not emit file edits as prose. The tool executes JavaScript in the isolated realm runner. Each `realm.fs` call goes to the host, which reads files in the given realm and saves each write before the call returns.

The script runs in a small QuickJS sandbox, not in Node.js or a browser. The script is the body of an async function, so you can use `await` and `return` at the top level. The only globals that the sandbox adds are `realm` and `room`; the standard JavaScript built-ins (`JSON`, `Math`, `Date`, `RegExp`, `Promise`, and so on) also work. There is no `console`, `print`, `nodeRepl`, `process`, `require`, `import`, `fetch`, `setTimeout`, DOM or Node API. A call to one of these stops the script with a `ReferenceError`. The tool result shows only the value that the script returns, as JSON, and nothing else. To see a value, `return` it, for example `return { files: await realm.fs.list() };`. A script that does not return a value gives a result with no value.

Before editing, read the current contents of every target file with `await realm.fs.readText(path)` in the script. To see what a folder holds, call `await realm.fs.list(path)`; with no path it lists the realm root. It returns one `{ name, path, kind }` entry for each file and folder directly in that folder, where `kind` is `'file'` or `'directory'` and `path` is relative to the realm root (a folder's `path` ends with `/`). To read a card instance as data, call `await realm.cards.get(path)`, where `path` is the instance with or without `.json` (`Person/sample`). It returns `{ id, path, type, attributes, relationships }`: `type` is `{ module, name }` of the card's definition, `attributes` holds the field values, computed fields included, and `relationships` maps each link's field path to the linked card's URL (`field.0`, `field.1`, … for a `linksToMany` field). Every URL is absolute. It reads the indexed card, so a card you just wrote can take a moment to index; then it fails with `Card is not indexed yet`, and you read it again. It also fails for a card that is not found or has an error, with that error's message. To read or list without writing, return the result from the script, for example `return await realm.fs.readText('person.gts');`, and read it in the tool result. Pass the workspace realm URL and room ID supplied by the host. Use `await realm.fs.replace(path, exactCurrentText, replacement)` for an existing file. Use `await realm.fs.writeText(path, content)` for a new file; it refuses a file that already exists. `path` is relative to the realm root, such as `person.gts`; a full file URL inside the realm also works. File content often contains backticks and `${`, for example a BXL `fx` expression or a template string in a computed field. If you put such content inside a JavaScript template literal, escape each backslash in it as `\\` first, then each backtick as `` \` `` and each `${` as `\${`. Without this, the script does not parse, or it saves different text without an error: `/\d+/` becomes `/d+/`, and `${name}` is replaced with a value. Escape the `exactCurrentText` argument of `realm.fs.replace` the same way, or it does not match the file. Use `await realm.fs.writeBytes(path, base64)` for a new binary file, such as an image: `base64` is the file's bytes as a base64 string, or a `data:` URL with base64 content. It refuses a file that already exists, a file larger than 2,000,000 bytes, and more than 5,000,000 bytes in one call. `readText` and `replace` refuse a binary file. Use `await realm.fs.delete(path)` to delete a file that the same `run-realm-code` run created with `writeText` or `writeBytes`, such as a file the script wrote by mistake. It refuses every other file: a file that was there before the run, a file that an earlier run created, and a folder. The tool result lists the file with the status `deleted`, and the file does not exist. After the delete, the same script can write the path again with `writeText` or `writeBytes`; the tool result then lists the file as saved. A path counts once toward the 20-file limit, however many calls use it, so a delete and a new write to the same path count as one file. No call deletes a file that an earlier run saved. To fix such a file, change its content with `realm.fs.replace`. To put its content at a different path, write a new file there with `writeText`, then tell the user which old file to delete. Use `await realm.fs.exists(path)` to check whether a file exists. Await every call. Write all files of a build in one call, within the limits of one call: at most 20 files (each file path given to `readText`, `exists`, `replace`, `writeText`, `writeBytes`, `delete`, `images.generate` or `download` counts; `list` and `cards.get` do not; a path counts once, however many calls use it, and each image counts once, as the path it is saved at), a script of at most 100,000 characters, and 55 seconds. Split a larger build across calls. To show the user a card when the run ends, return `{ show: path }` with the instance path, for example `return { show: 'Pet/mango' };`, from the call that writes it; there is no separate call to show it. The host opens it after it checks that the card is an instance in this realm; if it cannot, the result's `showError` says why and the files stay saved. A `.gts` or `.ts` write with lint errors that autofix cannot repair is refused, and the script stops there. Each write is saved when its call returns, so if the script fails partway, the files written before the failure stay saved; the error names them. The error names in a separate list the files that the run created and then deleted before the failure; those files do not exist. After the run, `realm.fs.delete` cannot remove a file the failed run saved: fix it with `realm.fs.replace` in the next run, or tell the user which file to delete.

To look at what the script made, call `await realm.capture(target, options)` after the write. `target` is a path in this realm, or a card id or file URL in any workspace the user can read, such as a catalog card or a file in another workspace; a target in no readable workspace is refused. `options` is optional: `format` (`isolated`, the default, or `embedded`), `viewportWidth`/`viewportHeight` (default 1280×800) and `fullPage`. To see a card, view an instance (`Person/sample` or `Person/sample.json`); viewing a `.gts` path shows the module's source file, not the card it defines. It attaches the image to the tool result, so you see it alongside the result; the script gets back only `{ path, kind, format, width, height, attached }`, never the image. A run can capture at most 3 times, and each capture spends the run's 55 seconds; a fourth capture, or one with too little time left in the run, is refused: capture the rest in another run. A card you just wrote can take a moment to index; if its capture fails, capture it again in your next run.

To find what exists across realms and the catalog — Specs, cards, files, listings — call `await realm.entries.search(query, { realms, scope, limit })`. `query` is a card query, without `page`: a `filter` built from `on`/`type`, `eq`, `contains`, `range`, `in`, `any`, `every`, `not` and full-text `matches`, and an optional `sort`; the syntax is in `boxel-environment/references/searching-and-querying.md`. A query with `page` is refused. `realms` is an array of realm URLs and defaults to every realm the user can read, the catalog included; `scope` is `'cards'`, `'files'` or `'all'` (the default); `limit` is how many entries to return, 20 when missing and never more than 50. It answers `{ entries, total, truncated, incomplete }`. Each entry is `{ url, kind, ref, specType, cardTitle, cardDescription, name, readMe }`, where a Spec's `ref` is the export it describes and `readMe` is its full readMe. `truncated` is `true` when more entries match than the answer holds: narrow the query rather than ask for more. `incomplete` is `true` when a realm did not answer. The search does not write and does not count toward the 20-file limit. Run all the searches a task needs in one script and return only what you will use; see `boxel-ui-component-discovery` for a loop.

To make an image, call `await realm.images.generate({ prompt, path, sourceImageUrl, llmModel })`. `prompt` and `path` are required; `sourceImageUrl` (an image to start from: a `data:` URL, or a file in this run's workspace, as a path or a full URL; any other URL, such as a public `http(s)` image, is refused) and `llmModel` (an image model id) are optional. The host asks the model for the image and saves it as a new file at `path`; the file extension follows the image type the model returns, so `Pet/mango.png` can be saved as `Pet/mango.jpg`. Before it asks the model, it refuses a path where a file already exists, also with another image extension (`Pet/mango.jpg` blocks `Pet/mango.png`), so no credit is spent on an image that cannot be saved. It returns `{ path, contentType, size, saved: true }`, never the image: link the returned `path` in the card JSON in the same script. `path` is relative to the realm root, so a link from an instance in a folder needs `../` in front of it (`sample-images.md` in `boxel-file-def` has the steps). Each image spends the user's credit, so a run whose code contains `realm.images.generate` always waits for the user to approve it, also in act mode; write the call exactly by that name, because a run that gets to it in a different way is refused. A run can generate at most 4 images, and a run that generates images gets 120 seconds for them on top of its 55 seconds, at most 60 seconds for each image. The realm calls of a run go one at a time, also in `Promise.all`, so the images are made one after another within those 120 seconds; when the time is used, the next call is refused before it asks the model.

To save a file from the web into the realm, call `await realm.fs.download(sourceUrl, path)`. `sourceUrl` is an absolute `http` or `https` URL. `path` must have a file extension, because the realm infers the file type from it. The host fetches the file and saves it; the bytes never enter the script. It refuses a file that already exists, an empty response and a failed fetch, a file larger than 10,000,000 bytes, and more than 25,000,000 bytes in one run. Each download may take 20 seconds, and it counts toward the run's 55 seconds. It returns `{ path, size, saved: true }`; link the returned `path` in the card JSON in the same script. A run whose code contains `realm.fs.download` always waits for the user to approve it, also in act mode; write the call exactly by that name, because a run that gets to it in a different way is refused.

To refresh the index of this realm, call `realm.index`. `await realm.index.invalidate(paths)` indexes specific files again (a path, or an array of 1 to 100 paths); `await realm.index.reindex()` reindexes the realm; `await realm.index.fullReindex()` rebuilds the whole index from scratch; `await realm.index.cancelJob()` cancels the running indexing job. Each call needs write access, starts the work on the realm server and returns at once, with no wait for the indexing to finish. Use them when a card shows old data or an index error after an edit and the user asks to refresh it. Each call returns a small object when the realm server accepted the request (`{ invalidated: [paths] }`, `{ reindex: 'started' }`, `{ fullReindex: 'started' }` or `{ cancelled: true }`) and throws with the server's error when it did not. A cancel stops the indexing jobs the realm is running; jobs that wait in the queue stay there and run after it. A full reindex is slow and a cancel leaves the index without the work it stopped, so use them only when the user asks. A run whose code contains `realm.index.fullReindex` or `realm.index.cancelJob` always waits for the user to approve it, also in act mode; write these calls exactly by that name, because a run that gets to one in a different way is refused.

To create a workspace for the user, call `await realm.workspaces.create({ name, endpoint })`. Both options are optional: a random name is made when `name` is missing, and `endpoint`, the URL path segment, is made from the name when it is missing. It returns `{ url, name }`. Report the URL to the user. When the run ends, the host opens the new workspace. A run works in one realm only, so the script cannot write to the new workspace. To add files to it, run `run-realm-code` again with the new URL as `realm`. One run can create at most 5 workspaces.

To delete a workspace that the user owns, with all of its cards and files, call `await realm.workspaces.delete(url)`. It returns `{ url, deleted: true }`. A delete cannot be undone, so confirm with the user before you call it. Write the call exactly as `realm.workspaces.delete(...)` in the script. A run whose code contains that text always waits for the user to approve it, also in act mode. A run that gets to the delete in a different way is refused.

To run a command that a skill enabled in this room declares, call `await realm.commands.run({ module, name }, { attributes, relationships })`. `module` and `name` are the command's `codeRef` as the skill declares it (`name` is `default` when it is missing). The input has the same shape as the payload of a tool call: `attributes` holds the field values, and `relationships` holds each linked card as `{ links: { self: url } }`. The call returns the command's result as `{ attributes, relationships }`, or `null` when the command returns nothing. The command does its own checks and can change files in this realm or in another realm, so read a file again after the call before you edit it. Only a command that a skill enabled in the room declares can run. A command whose declaration has `requiresApproval: true` is refused (call it as a tool instead, so the user can approve it), and so is a host tool (`@cardstack/boxel-host/...`). The command's time counts toward the 55 seconds of the run, and the files it writes do not count toward the 20-file limit. If the run fails after a command ran, the error names the commands that already ran; do not run them again.

To change this chat room, call `room` in the script. `await room.enableSkills([id, ...])` turns skills on and `await room.disableSkills([id, ...])` turns them off; an id is a skill card id or a skill markdown file URL, at most 20 in one call. `await room.setModel(modelId)` switches the room to another model, such as `anthropic/claude-sonnet-4.5`; a model the room cannot use is refused with the list of models it can use. These calls change only the room the tool was called from. Each call checks its input and records the change; the host makes the changes after the script finishes, and only when it finishes without an error. An error the script catches itself does not count: when a `try/catch` around the call returns normally, the changes are made. The tool result lists each change that was made. A skill you enable is available from your next step.

To show the user what the script made, ask for UI actions with `realm.ui` in the same script: `await realm.ui.switchSubmode('code')` (or `'interact'`), `await realm.ui.openFile(path)` to open a file in code mode, `await realm.ui.previewFormat(cardPath, format)` to open a card's definition with a preview of that card (`format` is `isolated`, `embedded`, `fitted`, `atom` or `edit`; `cardPath` is the instance path, such as `Pet/mango`), and `await realm.ui.openWorkspace()` to open the workspace the script runs in. Each call checks its input when the script makes it, so a missing file fails at once. The host does the actions in order after the script finishes, and only when it finishes without an error; a run can ask for at most 10. The result's `uiActions` gives the status of each action. This replaces a separate `switch-submode`, `preview-format` or `open-workspace` call after a build.

`run-realm-code` also runs in a workspace the user can only read, such as a catalog. There, reads, lists and captures work, and each write is refused with `You can only read this workspace`. Do not retry a refused write in the same workspace: tell the user, or write to a workspace the user owns.

Keep the script deterministic and narrowly scoped. Do not access browser globals, network services (other than through `realm.fs.download`), credentials, or files outside the given realm (other than through `realm.entries.search` and `realm.capture`). After the tool returns, inspect its result and address any correctness errors with another tool call.
